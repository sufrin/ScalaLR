# Bootstrapping

The production `scalalr` program evolved through a sequence of "bootstrapped"
versions of increasing quality and generality. 

  1. **Bootstrap:** The very earliest version 
was a prototype whose input notation (and hand-built parser) was inflexible, and whose error-handling
during parser generation was not of production quality. It allowed us
to test our conjecture that Bison could be sensibly used as a
table-generating workhorse, and to develop a sensible parsing API. 
More importantly, it allowed us to develop...

  2. **Stage 1:**
This version uses a formal (scalalr) description of the scalalr input notation, with the same
parser-generation module as the bootstrap. It made experimentation with the input
notation more straightforward, and led to a few innovations in the parser-generation module
that were straightforwardly retrofitted to the bootstrap.

  3. **Stage2:**
  This version uses a *completely re-engineered* parser generation module, and a
  very flexible and adaptable scalalr description of scalalr input notation.

### Getting started (Developers)
The vast majority of developers working *on* scalalr will be able to base themselves
on the current production version, and need never concern themselves with its 
history or the techniques used to evolve it. 

But if you are forced to start from scratch, here's how it should go:

  0. In `$ROOT/Prepare-bootstrap` the script `preparebootstrap.sh`
  handles the details of preparing a runnable `scalalrboot` processor
  and installing it in `$ROOT/scripts.`

  1. In `$ROOT/Prepare-Stage1` the script `preparestage1.sh`
  handles the details of preparing a runnable `stage1` processor
  and installing it in `$ROOT/scripts.`

  2. In `$ROOT/Prepare-Stage2` the script `preparestage2.sh`
  handles the details of preparing a runnable stage2 processor
  using the `stage1` processor to generate parsing components.

  3. After this, and in the same directory, the script `preparestage2-sh.sh`
  handles the details of preparing the self-hosted runnable stage2 processor
  using the `stage2` processor to generate parsing components.

  4. After this, and in the same directory, the script `generatescalalr`
     handles the details of preparing the distributable `scalalr.jar`
     file that can be run by
````
        java -jar scalalr.jar [arguments]
````
## Stages 

In what follows we denote the provenance of 
the components generated by  a scalalr processor from a dialect of 
the scalalr input language by:

    (bootstrap.Syntax, bootstrap.Generator)(scalalrInputFile)

or just

    bootstrap(scalalrInputFile)

This denotes the components generated from `scalalrInputFile` by 
the bootstrap code-generator. The `scalalrInputFile` must be in
the  notation accepted by the handwritten bootstrap 
parser (which has become somewhat forgiving since this
document was originally written). The generated components 
are always placed under  a directory specified in the prologue of 
the input file.


### Stage 1: bootstrap
The bootstrapping sequence for `scalalr` starts with the bootstrap generator
constructed entirely by hand in `scala.` This is specified entirely (ie
input language syntax and output component semantics) by  objects of 
the `bootstrap` module, and the driver for the runnable program is 
`scalalrboot.scala.` 

We put these all together (from the `Prepare-bootstrap/` directory) 
using `sbt` to  package the dependencies for the bootstrap, then `scala-cli` to
construct a self-contained runnable for eventual placement in 
the `scripts/` directory. The script 

      preparebootstrap.sh

handles the (not very significant) details.

The runnable `scalalrboot` makes parser components for any notation 
described in the bootstrap `.scalalr` notation.  The generated components 
can be incorporated in any program  that needs a parser, and this parser is 
implemented by the `shared` module parsing  automaton `LRParser.` 

#### A complete example explained
A good place to find a complete example is

        $ROOT/examples/TinyFun

in which the script `maketinyfun` uses the bootstrap scalalr followed
by `scala-cli` to generate a runnable program. In advance of this you
should run `sbt "clean ; package"` in the root directory of the distribution:
```
        ROOT=../..
        [ ! -e ROOT ] && ln -s -f $ROOT ROOT            
        # Symbolic link from ROOT in this directory to the distribution root
        scalalrbootstrap tinyfun.scalalr
        scala-cli --power package -f -o runtinyfun runtinyfun.scala TinyFun.scala generated
`````
The scala source `runtinyfun.scala` uses `scala-cli` directives to
establish the classpath:

        //> using scala 2.13
        //> using jar ROOT/bootstrap/target/bootstrap-0.8.0.jar
        //> using jar ROOT/shared/target/shared-0.8.0.jar
        //> using jar ROOT/utilities/target/utilities-0.8.0.jar
        //> using jar ROOT/logging-api/lib/Logging.jar
        //> using dep org.scala-lang.modules::scala-xml::2.4.0

        object runtinyfun { ... }

The `jar` references are to jars constructed for
the individual modules by the abovementioned 
        
        sbt "clean ; package"

### Stage 1 (FLaB)
The next stage (First Language after Bootstrap) is the
first stage at which  `scalalr`-generated parser components
can be incorporated into a processor for a dialect of the `scalalr`
notation. There are two possibilities for building
generator components. 

      stage1 = bootstrap(stage1-notation.scalalr)

      stage1 = bootstrap(forgiving-stage1-notation.scalalr)

We prefer the second: but whatever choice is made, the resulting `stage1` does no more 
after parsing the notation description than translate `stage1` abstract
syntax into bootstrap abstract syntax, then invoke the `bootstrap.Generator.`
So there is no practically-discernable difference between code
generated by the bootstrap and the stage1 scalalalr programs,
and we can legitimately say that at this stage we have a self-hosting 
scalalr *based on the bootstrap component generator and abstract syntax.* 




### Stage 2 (SLaB)
The next stage  (Second Language after Bootstrap) incorporates a re-engineered
component generation phase, and a modernised notation description. 

        stage2 = stage1(stage2-notation.scalalr)

From this point on stages can be self-hosted, *ie* generate the parser components that they will
incorporate when built.

Our policy henceforth will be to keep the core stage2 language and semantics stable. Further
developments will be straightforwardly backward compatible.
